== Deployment View

Die Verteilungssicht beschreibt die physische Zielumgebung, die ausführenden Hardwareknoten, die Softwarebausteine sowie die verwendeten Netzwerk- und Verbindungskanäle.

=== Infrastruktur und Verteilungsdiagramm

Das Gesamtsystem wird primär auf einem lokalen Arbeitsplatzrechner (*Host-PC*) ausgeführt. Optional ist der physische Roboterarm *MyPalletizer 260 M5* über eine serielle USB-Verbindung angeschlossen.

=== Knoten und Infrastrukturelemente

[cols="1,1,3", options="header"]
|===
| Knoten / Element | Betriebssystem / Typ | Technische Beschreibung und Voraussetzungen

| **Host-PC**
| Windows 10/11, Linux (Ubuntu 22.04+), macOS (12+)
| Standard-Entwicklungsrechner. Führt sowohl die Python-Steuerung als auch die Unity-Simulationsanwendung aus.

| **Python-Laufzeitumgebung**
| Python 3.12 oder neuer
| Verwaltet das installierte Paket `mypalletizer-api` sowie die Abhängigkeiten `numpy` und `pymycobot`.

| **Unity-Laufzeitumgebung**
| Standalone-Build oder Unity Editor
| Führt die vorkompilierte Simulationsanwendung aus. Benötigt Unterstützung für OpenGL / DirectX / Metal sowie freie lokale UDP-Ports.

| **MyPalletizer 260 M5**
| Embedded System (ESP32 / M5Stack)
| Physischer 4-Achs-Roboter mit interner Echtzeit-Servosteuerung und Relais-Ausgängen für Werkzeuge.
|===

=== Kommunikationskanäle

[cols="1,1,1,3", options="header"]
|===
| Kanal | Verbindung | Format / Baudrate | Zweck und Charakteristik

| **Roboterkanal**
| UDP Socket (`127.0.0.1:5005`)
| UTF-8 JSON Datagramme
| Zeitkritische Übertragung von Gelenkwinkeln, LED-Farben und Werkzeugzuständen. Verbindungslos, latenzoptimiert.

| **Weltkanal**
| UDP Socket (`127.0.0.1:5006`)
| UTF-8 JSON Datagramme
| Übertragung von administrativen Szenenkommandos (`spawn`, `delete`, `clear`). Getrennt vom Roboterkanal zur Vermeidung von Latenzspitzen.

| **Hardware-Kanal**
| USB-zu-Serial-Verbindung
| 8N1, `115200` Baud
| Übertragung von Steuerbefehlen an das M5Stack-Mainboard und Empfang von Gelenkwinkeln zur Telemetrie.
|===

=== Bereitstellungs- und Deployment-Szenarien

Das System unterstützt drei typische Einsatzszenarien:

1. **Reine Simulationsumgebung (`virtual`):**
+
* **Zielgruppe:** Studierende im Fernstudium, Entwickler ohne physischen Roboter.
* **Komponenten:** Python-Skript und Unity Standalone Executable (oder Unity Editor) auf demselben Host-PC.
* **Vorteil:** Komplett ortsunabhängig, kein Hardware-Setup erforderlich, kein Beschädigungsrisiko.

2. **Hybrider Parallelbetrieb (`both`):**
+
* **Zielgruppe:** Praktika an der HSLU, Validierung vor realen Produktionsabläufen.
* **Komponenten:** Python-Skript, Unity-Simulation und physischer Roboterarm zeitgleich über USB verbunden.
* **Vorteil:** Direkter visueller Echtzeitabgleich zwischen mathematischem Modell und realem Verhalten.

3. **Reiner Hardwarebetrieb (`real`):**
+
* **Zielgruppe:** Finale Ausführung fertig getesteter Steuerprogramme auf der realen Hardware.
* **Komponenten:** Python-Skript und MyPalletizer 260 M5 (Unity muss nicht gestartet sein).
* **Vorteil:** Minimale Systemlast, da keine 3D-Engine gerendert werden muss.

=== Softwareverteilung und Paketierung

* **Python-Paket (`mypalletizer-api`):** Wird über `pyproject.toml` als standardisiertes Python-Wheel gebaut und kann via `pip install .` oder im Entwicklungsmodus (`pip install -e .`) installiert werden.
* **Unity-Anwendung:** Wird über automatisierte GitHub Actions als eigenständige Standalone-Binary für Windows (`.exe`), Linux (`.x86_64`) und macOS (`.app`) erzeugt und als Release-Artefakt bereitgestellt.
